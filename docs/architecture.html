Claude Code Orchestrator

A local Next.js dashboard that runs autonomous Claude Code agents against the GitHub issues of any number of local repositories. All intelligence comes from the Claude Agent SDK (the Claude Code harness as a library); the orchestrator supplies the workflow, guardrails, and UI around it.

The orchestrator itself stores only the repo registry. Everything else (tasks, logs, goal, memory, planning history, worktrees, personas) lives inside the managed repo, so removing a repo from the registry loses nothing and re-adding it restores everything.

Task lifecycle

ready ──(Start button)──▶ working ──▶ committed ──(Push & open PR)──▶ pr_open
                            │   ╲                       ▲
                            │    ╲──▶ failed ──(Retry)──┘ (reuses worktree)
                            ▼
                       needs_input  (session paused on a question; reply resumes it)
  • Discovery: the loop polls gh issue list per repo; every open issue becomes a ready card. Nothing starts automatically.
  • Start: creates <repo>/.worktrees/issue-{n} on branch agent/issue-{n} (based on the repo's actual default branch, resolved from origin/HEAD), then launches one SDK session with cwd = the worktree.
  • Finish: agents only ever commit. A clean finish is committed; pushing and PR creation happen exclusively from the dashboard. Status is mirrored to GitHub labels (agent-working, agent-committed, agent-pr, agent-failed, agent-needs-input).

Under the hood: the task prompt

Every session receives one composed user message (src/server/task-prompt.ts). Its anatomy:

You are an autonomous engineering agent working on GitHub issue #{n} …
Your working directory is the git worktree at {path}, branch `agent/issue-{n}`.

Workflow:
1. Read the issue first (gh issue view {n} --comments) — it is the full spec.
2. Follow the repository's CLAUDE.md conventions.          ◀ loaded automatically:
3. Implement the change.                                     the session runs the
4. Verify with lint and unit tests ONLY (never e2e,          `claude_code` system-
   never migrations, never deploy commands).                 prompt preset
5. Before committing, ALWAYS request reviews from BOTH the
   `code-architect` AND `data-privacy-reviewer` agents       ◀ resolved from the
   (in parallel); apply confirmed findings, re-verify.         repo's .claude/agents
6. Commit with conventional commits.
7. STOP after committing. NEVER push, NEVER `gh pr create`.

If blocked on a decision only the developer can make, call `ask_user` once.
If you learn a reusable lesson, call `save_memory` once (one sentence).

## Project goal          ◀ injected from <repo>/.orchestrator/goal.md
…vision + current priorities…

## Lessons from previous agent sessions   ◀ injected from memory.md
…curated, agent-appended `- [#n] lesson` lines…

The rendered prompt is stored on the task (the "Task prompt" panel in the UI) and logged as a highlighted prompt event, so you can always see exactly what an agent was told.

Custom tools (in-process MCP)

ToolWhat happens
ask_user(question)Task flips to needs_input; the tool call is held unresolved until you reply from the UI, then the answer becomes the tool result and the same turn continues with full context.
save_memory(lesson)Server appends - [#n] lesson to the repo's memory.md: the only write path into memory; agents cannot touch .orchestrator/ directly.

Permission model

  • permissionMode: 'acceptEdits' plus a canUseTool callback (deliberately not bypass mode, so the callback is always consulted).
  • File tools (Read/Write/Edit/Glob/Grep) are confined to the issue's worktree; credential dotfiles and out-of-worktree .env* are denied.
  • Bash deny-list: all git push variants (incl. +branch force forms), gh pr create, workflow dispatch, deploy/prod-DB patterns, remote-host psql; curl/wget/WebFetch restricted to GitHub hosts.
  • SDK stream events are mapped to compact log lines (tool + command/path only, never file contents) and streamed to the UI over SSE.

  • Personas are repo content: <repo>/.claude/agents/principal-engineer.md and product-manager.md are read at runtime, so each repo tailors its own planning perspective. Both ground themselves in the repo's goal file and the open GitHub backlog (mandatory dedupe) before proposing.
  • Exclusion digest: every prior proposal (dismissed / pending / filed) is prepended to both persona prompts and to the synthesizer as a backstop, so passes don't re-propose what you already rejected or queued. Dismissed items may only return with explicitly stated new evidence.
  • Models: planning runs on claude-fable-5; on a usage-limit error it retries once on claude-opus-4-8.
  • Scheduling: on demand, or auto-run every N hours while the app is running.

Security model

  • Server binds 127.0.0.1 only; a global middleware enforces a localhost Host/Origin check on every API route (including GETs and SSE), closing CSRF and DNS-rebinding paths.
  • Execution agents: worktree-confined file access, command deny-lists, GitHub-only egress. Publishing (push, PR, issue creation) happens only through dashboard actions you click.
  • Planning agents: read-only by construction. No file-writing tools; Bash restricted to list/view/grep-style commands.
  • Auth is delegated: GitHub via your gh login, Claude via your Claude Code login/API key. The orchestrator stores no secrets.
